why

An agent on your machine is an agent on your life

A coding agent is a shell with your permissions. Hand it your computer and you hand it your keys, your files and your secrets.

on the hostWhat it can reach

Everything the agent's user can reach, and the agent never asks.

  • ✕Your SSH keys, your .env files, your cloud credentials
  • ✕Your projects, your notes, your browser sessions
  • ✕A wrong command that deletes the wrong directory
  • ✕A system left dirty, with packages and files everywhere
  • ✕Your tokens, sent wherever the prompt takes it

in the boxWhat it can reach

The guest filesystem, and nothing else. The boundary is the kernel.

  • ✓The files of the virtual machine, and the shared folder
  • ✓Your projects, but the copies inside the guest
  • ✓A wrong command that breaks the guest, and nothing else
  • ✓A snapshot to go back to
  • ✓A box you delete without a second thought
isolation

Why a virtual machine, and not a container

A container is a process with a few walls around it. A virtual machine is another computer. When the agent is the one you do not trust, that difference is the whole point.

what
a container
a virtual machine
Kernel
Shared with the host
Its own, in the guest
Files
The host filesystem, unless you mount it very carefully
Only the guest filesystem
Escape
A container escape is a host compromise
The guest kernel is the wall, root included
Devices
The host devices, if you are not careful
Emulated, with your permission
Blast radius
The whole workstation
One disposable disk
Reset
Delete the container, lose the work
Revert a snapshot, keep the work
→ A container is fine to isolate a build. It is not fine to isolate an agent that writes its own code and runs it. AIBox uses a virtual machine, and a real kernel, for that reason.
playground

A playground you can break and throw away

The point is not only to protect the machine. It is to give the agent a place where it can try things — and to make that place easy to create, easy to reset and easy to share.

1

One-command setup

A guided setup builds the guest, the SSH access, the services and the tunnel, step by step.

2

Snapshots and resets

Snapshot before a risky run, revert in a click, and keep the broken state around to study it.

3

A local web console

Services, updates, setup steps, snapshots and the VM lifecycle, in a tab that stays on your machine.

4

VS Code Remote-SSH

Open the shared folder in your own VS Code. The host path is mapped to the guest path for you.

5

One tunnel per service

Each service gets its own port forward and its own bind address. Localhost by default, the network only when you ask.

6

LAN exposure on demand

Expose a single service to the network, per service, without opening the whole VM to the world.

7

Your harnesses, installed

The setup installs opencode, the DeepSeek Harness and Claude Code in the guest, and registers their services for you.

8

Updates you can see

Check the host and the VM for updates, then apply them one target at a time — a service, a script, the OS or all of them.

network

One door into the box

The VM is never exposed directly. Every service travels through a single SSH tunnel, and only the services you choose can leave the machine.

how it works

Three commands and you have a box

Clone the repository, run the setup, then pick how you want to work: the shell, the console or VS Code.

step 1

Set the box up

The setup walks through the VM, SSH, the services and the tunnel. Every answer is saved, so a second run only asks what changed.

clone & setup 
git clone git@github.com:malko/aibox.git
cd aibox && ./setup.sh
step 2

Open a shell in the guest

One command opens an SSH session in the virtual machine, with every service already forwarded to the right local port. This is where your agent works.

connect 
./aibox
step 3

Or drive the box from the browser

The local console shows the services with a live availability dot, and gives you the VM controls, the snapshots and the updates.

web console 
./aibox web
the console

The web console, in three views

The same state the CLI shows, in a browser tab that stays on your machine — no account, no server, no telemetry.

requirements

Almost nothing

A Linux host with KVM, and a guest image. That is the whole list.

host

  • KVM/QEMU with libvirt
  • virsh and libvirt-client
  • BusyBox httpd for the web console
  • A Linux distribution, on bare metal or on a workstation

guest

  • Ubuntu or Debian, with SSH access
  • 4 GB of RAM, 4 cores recommended
  • A dedicated user with sudo rights
  • The share is mounted with virtiofs
→ macOS is not supported yet. The Lima based support is being finished, and it will land here.
faq

The questions people actually ask

Short answers, no marketing.

Can the agent reach my files?
Only the ones you put in the shared folder, and the ones inside the guest. Your SSH keys, your browser sessions and the rest of the workstation stay out of reach: the agent works in a virtual machine with its own kernel.
Why a virtual machine and not Docker?
A container shares the kernel and the filesystem of the host: a container escape, or a badly written mount, hands the agent your whole machine. A virtual machine has its own kernel, and that kernel is the boundary. For a build, a container is enough. For an agent that writes and runs its own code, it is not.
What if the agent breaks everything?
You take a snapshot before it starts, and you revert it afterwards. The broken state stays available to look at, and the host never saw any of it.
Does any of my data leave the machine?
No. The VM runs on your hardware, the console is served by BusyBox on your machine and the tunnels are plain SSH. There is no account, no telemetry and no cloud service in the loop.
Do I need root on the host?
Only for a few setup steps, and the console asks for the sudo password once, in memory, when a privileged step needs it. Everything else runs as your user.
Can I run my own services?
Yes. aibox service-add mytool 8080 registers a port, and the tunnel, the console and the status output pick it up right away.
How do I reach a service from another device?
Expose that service on the LAN: aibox tunnel lan on opencode --permanent. The tunnel binds the port on your network interface instead of localhost, for that service only.
Is macOS supported?
Not yet. The Lima based support is on its way, and the site will say so as soon as it works.
